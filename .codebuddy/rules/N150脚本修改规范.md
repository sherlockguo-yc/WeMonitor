# N150 脚本修改规范

## 规则

修改 N150 上的任何 shell 脚本（`~/deploy-agent.sh`、各项目 `restart.sh`、`webhook-start.sh` 等）时：

0. **优先改源头仓库**：`restart.sh` 等随 CI 产物分发的脚本，修改必须改源头仓库并 `git push` 触发 CI 自动部署。N150 现场修改只能救急，会被下次 `rsync --delete` 覆盖回旧版（2026-08-07 复发案例：08-06 现场改的 `9>&-` 未同步到源头仓库，被后续正常部署覆盖，flock 死锁复发并阻塞所有项目部署队列 1 天）。仅 `~/deploy-agent.sh`、`~/webhook-start.sh` 这类放 `~/` 下、不受 rsync 影响的脚本可直接现场改。

1. **禁止用 `sed -i` 做含 `&` 或 `$` 的替换**。`&` 在 sed 替换串中是特殊字符（代表整个匹配），叠加本地 shell（zsh）转义层后极易产生乱码（实际案例：`9>&-` 被破坏成 `9>--port "$PORT" > "$LOG" 2>&1 &- ...`）。
2. **首选 heredoc + stdin 完整写入**（`ssh n150 "cat > ~/xxx/restart.sh" <<'EOF'`），或把修改后的完整文件内容直接写入。字面传输，无转义问题。
3. 确需局部替换时，用 **python 脚本经 stdin 执行**（`ssh n150 "python3" < /tmp/fix.py`），字符串用单引号、避免反斜杠转义。
4. **备份 `.bak` 一次性覆盖即失效**：`cp a b && sed -i a` 中如果 sed 又写坏 a，再执行 `cp a b` 会把损坏内容覆盖进 b。备份后不要再执行覆盖备份源的写操作。

## 修改后必须验证（语法通过 ≠ 语义正确）

`bash -n` 只检查语法，**不检查语义**。实际案例中坏文件 `bash -n` 照样通过。必须：

1. `bash -n <file>` 语法检查
2. `diff` 或 `grep` 关键行确认修改内容正确（如 `grep -n '9>&-'`）
3. **实际运行验证**：触发一次真实执行（如手动跑 restart.sh 或等 cron 触发），确认 exit code 与日志输出符合预期

## 背景

2026-08-06 修改 `~/quiz-app/restart.sh`：用 `sed -i 's|...|...|g'` 加 `9>&-`，`&` 转义被本地 zsh 处理破坏，文件产生乱码；随后 `cp restart.sh restart.sh.bak` 又把损坏内容覆盖进备份。最终凭已知完整内容 heredoc 重建。整个过程浪费 3 轮交互，且乱码文件若被真实执行后果不可控。
