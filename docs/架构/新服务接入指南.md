# WeMonitor 接入指南

如何将一个服务纳入 WeMonitor 的部署状态监控和健康检查。

## 零、最快路径（2026-11-06 起）

WeMonitor 的部署监控清单直接读 N150 的 `~/.deploy-projects.conf`，
健康检查条目在启动时也从同一个文件自动补全。因此新增服务只需要：

1. 在 `~/.deploy-projects.conf` 加一行（格式见第三节）
2. 确保 N150 运行目录有 `restart.sh` 和可用的 `.version`
3. 在服务自己的仓库配好 CI（产出 Release + 通知 webhook）

不需要改 WeMonitor 的任何代码。下面第一、二节的操作只在两种情况下需要：
本地开发想看到 mock 数据（改 `FALLBACK_SERVICES`），或者要调整探测方式（改 `config.js`）。

## 一、部署状态监控

### 1. 数据来源

`lib/deploy/projects.js` 读取 `~/.deploy-projects.conf`，产出：

| 字段 | 来源 | 说明 |
|------|------|------|
| `id` | 第 1 列 PROJECT | 唯一标识，同时是 `.deploy-queue/states/<id>.json` 的文件名 |
| `name` | 内置显示名映射 | 未收录的项目按 id 原样显示 |
| `repo` | 第 2 列 REPO | GitHub 仓库 `owner/repo`，用于查询远端 Release |
| `dir` | 第 3 列 DIR | 运行目录（含 `.version`），`$HOME` 会被展开 |
| `port` | 第 4 列 PORT | TCP 探测目标，同时用于部署状态判定 |

文件不存在（如开发机）时 `readProjects()` 返回 `null`，`routes/deploy.js`
回退到内置的 `FALLBACK_SERVICES`。**回退清单只是开发兜底，不要把它当成注册入口**——
生产环境新增服务请改 conf，否则下次又会出现「部署页少一个服务」。

### 2. 状态计算逻辑

`computeSummary()` 按以下优先级判断状态：

| 优先级 | 条件 | 状态 |
|--------|------|------|
| 1 | 持久化队列中有进行中的任务 | `deploying` |
| 2 | 队列中有待处理任务 | `queued` |
| 3 | TCP 端口不通 | `stopped` |
| 4 | 最近一次队列任务为 failed / interrupted | `error` |
| 5 | 最近部署事件 status === `error` | `error` |
| 6 | 本地版本 == 远端版本 | `up-to-date` |
| 7 | 本地版本 ≠ 远端版本 | `update-available` |
| 8 | 无法判断（例如仓库不可访问、拿不到远端版本） | `unknown` |

## 二、健康监控

### 方式 A：自动同步（2026-11-06 起，推荐）

`lib/db.js` 启动时读取 `~/.deploy-projects.conf`，把每个项目的 `127.0.0.1:<PORT>`
作为 tcp 探测目标写入 `services` 表。**改 conf 就够，不用再手工插数据库。**

已有的同名服务由 `INSERT OR IGNORE` 跳过，通过 API 手工添加的条目（如 Webhook、
Portainer、aria2）不受影响。

### 方式 B：API 动态添加（需要自定义探测方式时）

```bash
curl -X POST https://wemonitor.sherlockguo.com/api/v1/services \
  -H "Content-Type: application/json" \
  -H "Cookie: <session>" \
  -d '{
    "name": "WeDownload",
    "scrape_url": null,
    "scrape_interval": 30,
    "health_type": "tcp",
    "health_target": "127.0.0.1:8080"
  }'
```

### 方式 C：固化为默认配置

`config.js` — 在 `defaultServices` 中添加。它只对「数据库里还没有同名记录」时生效，
常用于内置的核心服务：

```js
defaultServices: [
  // ...
  {
    name: 'WeDownload',
    scrape_url: null,          // 无 metrics 端点，设为 null
    scrape_interval: 30,       // 检查间隔（秒）
    health_type: 'tcp',        // 探测方式：目前只实现了 tcp
    health_target: '127.0.0.1:8080',  // 目标地址
    enabled: true
  }
]
```

各字段含义：

| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | string | 服务名称 |
| `scrape_url` | string\|null | Prometheus metrics 端点 URL，无则为 null |
| `scrape_interval` | int | 采集间隔（秒） |
| `health_type` | string | 目前 `lib/collector/health.js` 只实现 `tcp`，其它值会记为 unknown |
| `health_target` | string\|null | 探测目标地址，如 `127.0.0.1:8080` |
| `enabled` | bool | 是否启用监控 |

判断该用哪种探测时注意：SPA 服务（WeFood / WeDou）的 `/healthz` 会被前端 fallback
接住返回 `200 index.html`，用它探测会永远显示健康。这类服务一律用 `tcp`。

## 三、N150 端配置

### 1. `deploy-projects.conf`

在 `~/.deploy-projects.conf` 中添加一行：

```
wedownload|sherlockguo-yc/WeDownload|$HOME/wedownload|8080|sha|wedownload.tar.gz
```

格式：`PROJECT|REPO|DIR|PORT|TAG_MODE|FILE_NAME`

- `TAG_MODE: sha` — 按 commit SHA tag 查找 Release（`latest` 则用 latest tag）
- `PORT` 用于健康检查（lsof 检测），WeMonitor 也会用此端口做部署状态的存活探测

### 2. `restart.sh`

服务目录下必须有 `restart.sh`，`deploy-agent.sh` 部署完成后会调用它。示例：

```bash
#!/bin/bash
set -e
DIR="$HOME/<your-project>"
# 同步配置文件、复制 systemd unit、重启服务等
# 例如：
# sudo cp "$DIR/config/my-service.service" /etc/systemd/system/
# sudo systemctl daemon-reload
# sudo systemctl restart my-service
```

## 四、接入检查清单

- [ ] N150 `~/.deploy-projects.conf` — 添加项目行（部署监控 + 健康检查的唯一注册入口）
- [ ] N150 运行目录 `~/<project>/` — 确保有 `restart.sh`，部署后能写出 `.version`
- [ ] 服务仓库 — CI 产出 Release，并在构建完成后 POST 到 webhook
- [ ] N150 UFW — 若需内网访问，放行对应端口（`/firewall` 页面可操作）
- [ ] Cloudflare Tunnel — 若需公网访问，在 `/tunnel` 页面添加路由
- [ ] （可选，仅开发机）`lib/deploy/local.js` 加目录常量 + `routes/deploy.js` 的
      `FALLBACK_SERVICES` 加条目，让本地无 conf 时也能看到页面
- [ ] 验证：`https://wemonitor.sherlockguo.com/deploy` 出现新卡片，
      `https://wemonitor.sherlockguo.com/services` 出现健康检查记录
